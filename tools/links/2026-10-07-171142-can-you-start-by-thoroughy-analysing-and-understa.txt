  What it is

  Links-3 is a pipeline for one video site (fruitsvids.com). It scrapes video
  links per creator, sorts them into categories and duration buckets, shuffles
  them, then downloads batches through Chrome. The category and creator names in
  the files are placeholders (apple1, pear1, artist101…).

  necessary/: scrape and download

  - scrape_fruitsvids.py takes a creator URL and walks pages 1 to N, where N is
    the trailing number in the URL. It collects /videos/<slug>/ links plus each
    video's duration. It writes <creator>_links.txt with an ALL LINKS section
    and a CATEGORISED section (Pineapple, Orange, Pear, Other) based on keyword
    matches in the URL. It won't overwrite an existing file if a run finds 0
    videos, for example on a 503.
  - batch_scrape.sh holds about 95 creator URLs. It works out each expected
    *_links.txt filename and skips creators whose file already has more than 3
    links and a duration marker. It runs the scraper on the rest with a 2s sleep
    between runs.
  - scrape is a two-line wrapper that calls
    /Users/hugodyson/Links/scrape_fruitsvids.py, the old folder rather than this
    one.
  - vdh_auto.py picks 10 random links and opens each in Chrome via AppleScript.
    It then uses pyautogui to click the Video DownloadHelper icon at (1248, 95)
    and the Download button at (1177, 382). It doesn't track whether any
    download finished.
  - vdh_8_to_12.py and vdh_12_to_23.py do the same but wait for a new file in
    ~/Downloads. They then move it to
    /Users/hugodyson/instagram-bot-2/library/<creator>/, and keep going until 10
    downloads succeed or 30 attempts are used. The files differ only in the
    links file, the target folder (library/additions for 8_to_12) and the wait
    time (10s vs 25s).

  good too/: list processing

  These run in the folder holding the *_links.txt files.
  1. combine_all.sh merges every *_links.txt into all_links_ordered.txt and
     removes duplicates.
  2. split_categories.sh splits the files into
     all_links_ordered_{pineapple,orange,pear,other}.txt.
  3. split_by_duration_pineapple.sh splits the pineapple list into duration
     buckets (<8, 8–12, 12–23, 23–32, 32+ minutes, and unknown).
  4. randomise_pineapple.sh shuffles each bucket into *_random.txt, which the
     vdh_* scripts read. randomise.sh is an older version that shuffles only the
     pineapple list.
  5. pick.sh N [source] prints N random links from one of the lists.

  slug = re.sub(r"-(videos|exclusive-videos|videosis|new-videos)$", "", p)

  One note: regex alternation tries options in order, so videos matches first
  for -exclusive-videos. Since the pattern is anchored with $, it would strip
  only -videos and leave exclusive. To strip the whole suffix, put the longer
  options first: (exclusive-videos|new-videos|videosis|videos). batch_scrape.sh
  has the same ordering problem, so its filenames come out as
  artist1_exclusive_links.txt. The scraper has to match it exactly either way.
  If you'd like the cleaner names, change both files.

⏺ Yes, and it suits a UI well. The workflow is a fixed pipeline (scrape, sort,

  What a UI would fix

  - No overview: You can't tell which creators are scraped, how many links each
    has, or what's in each duration bucket without running wc -l.
  - Scattered controls: Settings like MAX_LINKS, TARGET_SUCCESS and the links
    file are hardcoded in the scripts, and you edit them by hand.
  - Hidden steps: Which scripts to run, and in what order, lives in your head.
  - Blind downloading: Downloads rely on fixed screen coordinates and give no
    live progress.

  Options

  Option: Local web app (Python backend, browser page at localhost)
  What it is: Wraps the existing Python logic; runs on your Mac
  Pros: Reuses your code, best-looking and easiest to extend, live progress easy
  Cons: Needs a server running
  ────────────────────────────────────────
  Option: Native-style desktop app (e.g. Tkinter or PySide)
  What it is: A window, no browser
  Pros: Single double-click app
  Cons: Plainer look, harder to polish
  ────────────────────────────────────────
  Option: Terminal UI (e.g. Textual)
  What it is: Menus inside the terminal
  Pros: Lightest change
  Cons: Still terminal, less visual

  My recommendation: the local web app. It would be a small Python server (Flask
  or FastAPI) that runs on your Mac and opens in your browser, with a simple
  page in front. I'd keep your scripts' logic, but tidy it into one importable
  module rather than shelling out to the .sh files.

  What the UI could contain

  1. Creators tab: the list of creators with link counts, last-scraped date and
     a status (done, needs re-scrape). Buttons to scrape one, scrape all
     missing, or add a URL.
  2. Library tab: category and duration filters with counts, replacing the
     combine, split and randomise scripts. It would build these views on demand
     instead of writing many .txt files.
  3. Download tab: choose a source (category, duration, creator), set how many,
     then start. It shows a live log, success and fail counts, and a stop
     button.
  4. Settings: the keywords, the library folder, the click coordinates, and a
     button to capture the coordinates by clicking on screen.

  Things to decide first

  - Storage: I'd move from many text files to one small SQLite file or a single
    JSON. It's cleaner, but your existing *_links.txt files would need importing
    once. Is that acceptable, or do you want to keep the text files as the
    source of truth?
  - Download method: the pyautogui clicking is the most fragile part. A UI
    doesn't change that. If the video URLs can be fetched directly (for example
    with yt-dlp), downloads would be more reliable and wouldn't need Chrome in
    front. I'd need to check that works for this site before promising it.
  - Fixing the bugs: I'd fix the slug and Pear issues as part of this.
  - Scope: a first version with Creators, Library and Download tabs, or
    everything at once?

  Two questions so I can plan it: do you want to keep the text files, and are
  you open to swapping the click-based downloader for something sturdier if it
  works?

  https://<domain>/video-creators/<creator-slug>/6/
  https://<domain>/models/<creator-slug>/3/
  https://<domain>/video-creators/<creator-slug>/?sort_by=<something>
  These are the same shapes as in your batch_scrape.sh list.

  - UI check: the UI only checks that the line starts with http:// or https://.
    Anything else is skipped as "not a URL".
  - Page count: a trailing number such as /6/ means "scrape pages 1 to 6". With
    no number, only page 1 is scraped. The "Pages" box in the UI appends that
    number for you.
  - Page URLs: the scraper builds them as <base>/ for page 1 and <base>/2/,
    <base>/3/ and so on for later pages. A site that paginates with ?page=2
    instead won't work.
  - Sort option: ?sort_by=… is kept. Any other query parameters are dropped.
  - Language prefix: a prefix like /es/ or /fr/ is allowed. It's ignored when
    naming the creator but kept in the request.
  - Creator name: it comes from the last path segment that isn't a number. The
    scraper currently strips -videos, -exclusive-videos, -videosis and
    -new-videos endings, depending on which version of that line is in your
    file.

  The domain

  The domain in the URL you paste is ignored. The scraper always requests pages
  from the domain hardcoded in build_page_url() (lines 60–61 of
  scrape_fruitsvids.py). It shows at the top of the UI as "Scraping: …". For the
  new site, change it there, once.

  What the page must contain

  For each video, the scraper needs:
  - a link whose address looks like /videos/<slug>/, which is what it collects
  - (optionally) a duration written as m:ss or h:mm:ss in the same card, in its
    own element. Without it the link is kept with duration ??, and it lands in
    the "unknown duration" bucket.

  What it won't read

  - An individual video page (/videos/<slug>/). That is the output, not an
    input.
  - Search results, or any page that doesn't use /videos/… links.
  - Pages that load their video list with JavaScript. The scraper doesn't run
    JavaScript.

  Different link formats would mean a change in scrape_fruitsvids.py, which is
  your file. If your new site's URLs differ, send me one example creator URL and
  one video URL and I'll tell you exactly what would need to change.

⏺ A slug is the part of a URL that names a page, in lowercase with hyphens
  instead of spaces. In https://site.com/video-creators/emma-clarke-new-videos/,
  the slug is emma-clarke-new-videos.

  How the scraper uses it

  get_creator_slug() turns a creator URL into the name for that creator's file
  and folder:

  1. Take the URL path and drop any language prefix (es, fr…).
  2. Walk the path from the end and take the first piece that isn't a number (so
     /6/ is skipped).
  3. Strip a trailing -videos, -exclusive-videos, -videosis or -new-videos.
  4. Replace hyphens with underscores.

  That result is the creator name, and it names the output file
  <slug>_links.txt. The UI shows the same name in the Creators table.

  What they come out as

  Your scraper's regex is currently
  -(videos|exclusive-videos|videosis|new-videos)$, so videos is tried first.
  Because of that, -exclusive-videos loses only -videos, and exclusive stays in
  the name:

  ┌─────────────────────────────────────────────┬───────────────────┐
  │                  URL path                   │   Creator name    │
  ├─────────────────────────────────────────────┼───────────────────┤
  │ /video-creators/artist1-exclusive-videos/6/ │ artist1_exclusive │
  ├─────────────────────────────────────────────┼───────────────────┤
  │ /video-creators/emma-clarke-new-videos/     │ emma_clarke_new   │
  ├─────────────────────────────────────────────┼───────────────────┤
  │ /models/artist104/                          │ artist104         │
  ├─────────────────────────────────────────────┼───────────────────┤
  │ /video-creators/lily-evans/                 │ lily_evans        │
  ├─────────────────────────────────────────────┼───────────────────┤
  │ /video-creators/zoe-carter-videosis/        │ zoe_carter        │
  ├─────────────────────────────────────────────┼───────────────────┤
  │ /models/artist102-videos/                   │ artist102         │
  └─────────────────────────────────────────────┴───────────────────┘

  So the same creator can get a different name depending on how the URL is
  written, for example /models/x-videos/ gives x while
  /models/x-exclusive-videos/ gives x_exclusive. If you list one person under
  two URL styles, they become two entries, and the library de-duplicates their
  links.

  Fixing the names

  Putting the longer endings first fixes it:
  r"-(exclusive-videos|new-videos|videosis|videos)$"
  I mentioned this earlier. It's your file, so I haven't changed it. If you edit
  it, the UI uses the new names on its next page load, though creators already
  added keep the name they were saved under.

⏺ Yes, but where the term lives decides how.

  Where "Orange" appears now

  - scrape_fruitsvids.py: ORANGE_KEYWORDS, the "Orange" category name, and the
    Orange print lines.
  - split_categories.sh: the --- Orange  heading it searches for, and the
    filename all_links_ordered_orange.txt.
  - pick.sh: the orange option and the same filename.
  - Existing data: every *_links.txt already has --- Orange (n) --- headings,
    and all_links_ordered_orange.txt exists as a filename.
  - The UI: its category names come from your script's variable names
    (ORANGE_KEYWORDS becomes "Orange") and from each site profile's category
    list.

  The problem

  The term is repeated in many separate files, and those files don't read from
  one place. A change in the primary file reaches the others only if something
  rewrites them. You asked me earlier not to touch your files, so any rewrite
  needs your say-so.

  Options

  1. Change it only in the UI (no original files touched). Category names live
  in the site profiles, so renaming Orange to Strawberry there already updates
  the library, filters, exports and picks, and old data is re-categorised on the
  fly. The old shell scripts keep saying "orange", but the UI replaces their
  jobs. Nothing is rewritten, so nothing can break. I could add a display-name
  box so a rename never needs a keyword edit.

  2. A "Rename term" tool in the UI that edits your files. You enter old and
  new, for example Orange to Strawberry. It handles the capitalised, lowercase
  and uppercase forms, preview-first:
  - It shows a dry run of every line and filename it would change.
  - It backs up every file to a folder in ui/ before touching anything.
  - It renames files too (all_links_ordered_orange.txt becomes …strawberry.txt).
  - It does whole-word matching only. This matters here: substring replacement
    of apple would corrupt pineapple, and your own apple1 exclusion keyword is
    already inside pineapple1.
  - You press a button to apply it.

  3. Refactor once so there is one source of truth. Put the category names in a
  small shared config that every script reads. That means editing each script
  once. After that, one change updates all of them. It's the cleanest long-term
  fix but the most invasive now.

  4. A background watcher that rewrites files whenever the primary one changes.
  I wouldn't. A half-saved edit, or a typo in the primary file, would be pushed
  across every file automatically.

  My recommendation

  Use option 1, which is already how the UI behaves, plus option 2 as an
  optional tool for when you want the original scripts and data kept consistent.
  Run it on a button press, not automatically. A button keeps a typo from
  spreading across all your files and leaves a backup if you change your mind.

  2. Which file is "primary" for you, scrape_fruitsvids.py? Should the tool read
     the old and new term from a pair you enter, or detect the change by
     comparing that file to its last saved state?
  3. Is it only the category names (Pear, Orange, Pineapple), or other words
     too?

❯ Currently, for the keywords, if a link has a word "laughing", but the keyword 
  is just "laugh", is the link incldued in that category or not? does it have   
  to be the exact word                                                          

⏺ Yes, it's included. The match is "contains", not "exact word".

  A keyword matches if it appears anywhere in the link, as a plain piece of
  text, in any case. So laugh matches laughing, laughter, laughs and
  she-laughs-a-lot. Laugh and LAUGH match too, because both sides are lowercased
  before comparing.

  It checks the whole link, not just the title. If laugh appears in the creator
  name or elsewhere in the URL, that counts too.

  Where this can bite you

  - Short words match inside longer ones. A keyword pear would also catch
    appearance, and ass would catch class. This is the same problem as apple1
    being inside pineapple1 in your original script.
  - Hyphens are just characters. The keyword laughing-out-loud only matches if
    the link has exactly those hyphens. A keyword laughing out loud with spaces
    would never match, because URLs use hyphens.
  - Order of categories matters. A link goes into the first category whose
    keywords match, in the order you list them. Anything in the "force Other"
    box is checked before all categories and wins.

  If you want stricter matching

  I can add an option, such as "match whole words only", so pear wouldn't match
  appearance. I wouldn't make it the default, because it would stop laugh from
  matching laughing, which is the behaviour you just asked about.

⏺ Yes, with one time limit to detect the file and a second timer for the
  download itself. It works like this:

  The first timer: waiting for a file to appear

  After the downloader clicks the download button, it checks your Downloads
  folder every 1.2 seconds for a new video file, .part or .crdownload. The limit
  is the "Wait for file to appear (s)" setting, 25 seconds by default. You can
  change it in Settings, so set it to 30 if you want.

  If no new file appears in time, it logs "No new file appeared" and moves on to
  the next link. That link isn't marked as downloaded, so it can be picked
  again on a later run.

  The second timer: a download in progress

  - If the new file is still downloading (a .crdownload or .part file), it waits
    up to 80 seconds for the finished file to appear, then moves it. That 80
    seconds is fixed. If it runs out, the file is left in Downloads and the link
    isn't counted.
  - If the new file is already a finished .mp4, it's moved straight away.

  Weak spots

  - A slow download can end up in the wrong folder. If link A's download appears
    after the 25-second wait, the downloader has already moved on. When link B
    starts, it takes a fresh snapshot of Downloads that may already include A's
    file or not. A file finishing during B's wait looks "new" for B and gets
    filed under B's creator.
  - A file that is still being written can be moved early. The downloader
    doesn't check the file has stopped growing. If the tool saves directly under
    its final .mp4 name and keeps writing, the move could catch it
    mid-download.
  - Timeouts drop the link silently, with no retry. It doesn't try that link
    again in the same run.

  If you'd like, I can fix these. The fixes would be a check that the file size
  has stopped changing before moving it, matching each file to the link it came
  from, and one automatic retry before giving up.

⏺ The scraper only reads the page's raw HTML, which is why it may or may not
  work on the new site. It doesn't open a browser.

  How it works

  For each page of a creator:
  1. It requests the page address directly, like a very basic browser. The only
     thing it sends is a Chrome-style identity string. It follows redirects, has
     a 20-second limit, and keeps no login or cookies beyond that one run.
  2. It reads the HTML it gets back and finds every <a href="…"> link on the
     page.
  3. It keeps the links whose address matches your video link pattern.
  4. For each one it looks in the same box on the page for text that looks like
     a duration, such as 12:34.
  5. It moves on to page 2, 3 and so on by building the next address from your
     "Next pages look like" format.

  So the links come only from <a href> tags that are already in the HTML the
  server sends.

  Where it can fail on a new site

  - The video list is built by JavaScript after the page loads. The raw HTML
    then has no video links, and the scraper finds none.
  - The site blocks scripts. It answers a plain request with an error (HTTP 403)
    or a "checking your browser" page instead of the real page.
  - An age or consent screen shows first. A real browser has clicked past it,
    and a plain request hasn't.
  - The links aren't in the shape you gave it. This is the easiest one to fix.

  How to check in about 30 seconds

  1. Open a creator page in Chrome and press Ctrl+U (Windows) or Cmd+Option+U
     (Mac) to see the page source.
  2. Search that source for part of a video's link or its title.
  3. If you find it, the scraper can see it. If you don't, the page is built by
     JavaScript and the scraper can't read it.

  The Try it box shows the same thing. Read its output like this:
  - HTTP 200, Matched as videos: 4: it works.
  - HTTP 403 or 503: the site is blocking it.
  - HTTP 200 but few bytes, or Links on page: 0: probably JavaScript or a
    consent screen.
  - HTTP 200, many links, Matched: 0: the video link pattern is wrong, and it
    lists the links it did see.

  If it turns out to be blocked

  There are options, in rising effort:
  1. Paste the page source: you save a creator page from your own browser and
     paste or import it. The UI pulls the links out of it. It always works, but
     it's manual for each page.
  2. Cookies or extra headers per site: this can get past an age screen by
     sending the same cookie your browser has. It may not help against heavier
     blocking.
  3. Read the page through a real browser: the scraper drives Chrome like the
     downloader does. It works on JavaScript pages but it's slower and heavier.
