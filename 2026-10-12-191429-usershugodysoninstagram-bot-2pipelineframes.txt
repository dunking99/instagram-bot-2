  What blocks it today
  - Both servers only listen on 127.0.0.1, so nothing but the Mac can reach
    them. That's lighttable_server.py:179 and server.py:103.
  - server.py:138 rejects any request whose Host header isn't localhost. That's

    block your phone.

    jobs, so you must not expose it as it is.
  - The UI is built for a desktop mouse and wide screens. Phone use needs
    responsive layout work, mainly the Search grid, the per-position creator
    lines and the Analysis rows.
  - server.py serves files with FileResponse, which handles Range requests in
    recent Starlette versions. Phone seeking and long clips should work, but I
    haven't tested that.

  Options
  1. Tailscale (recommended). Install it on the Mac and the phone. The Mac gets
     a private address that works from anywhere, including mobile data, and it's
     visible only to your own devices. It needs no port forwarding and no
     public exposure. The changes I'd make:
     - Bind to the Tailscale address.
     - Allow that address in the Host check.
     - Add a simple password or token as a second safeguard.
     - Fix the layout for phone width.
     - Add a home-screen icon through a PWA manifest, so it opens like an app.
  2. Same Wi-Fi only. Bind to the Mac's LAN address. It's the simplest option,
     but it only works at home, and anyone on that network could reach it unless
     I add a password.
  3. Native app (React Native or Swift). I don't recommend this. It's much more
     work and gains almost nothing over a PWA for a viewer and browser like

    on both devices.

❯ Is there a way to get frames every 5 seconds for a video, without having to   
  download the video at all?                                                    

⏺ In the strict sense, no. To see a frame you have to fetch some of the video's
  data. But you can fetch very little of it, and for some sources you don't need
  the video at all.

  Where it works
  1. A video served from a plain file URL (an mp4 on a server). ffmpeg can jump
     to a timestamp and read only the bytes around that frame, using HTTP range
     requests. For one frame every 5 seconds it typically reads a small
     percentage of the file, not all of it. Something like ffmpeg -ss 125 -i 
     "<url>" -frames:v 1 frame.jpg per timestamp. It's fastest when the file has
     its index at the start.
  2. A streamed video (HLS or DASH, the segmented kind most sites use). The
     video is split into small chunks. You can fetch only the chunks that
     contain your timestamps, and pick the lowest quality version to keep it
     small.
  3. Preview images the site already publishes. Many sites have a thumbnail
     strip or seek-bar sprite at regular intervals, and no video download is
     needed at all.

  Where it doesn't
  - Streams protected by DRM or signed, expiring links can't be read this way,
    and I wouldn't try to work around that.
  - I haven't checked what data18 exposes. Its "Video Stills" galleries are
    already frames from the video, but only about 29 per scene, not one every 5
    seconds. It may or may not provide a stream URL for one.

  What matters for you
  - Your own library videos are on disk, so extracting a frame every 5 seconds
    is already fast and local.
  - For data18 scenes, the stills are the practical source, and that's what the
    dashboard button uses. Getting finer coverage than that would need a video
    URL, and I'd have to look at what the site actually provides before saying
    it can be done.

  Is the source you're thinking of a data18 scene, or videos somewhere else?
